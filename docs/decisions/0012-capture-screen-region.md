# 0012: ライブ描画はウィンドウの ID ではなく、画面上のウィンドウの範囲を取り込む

- 日付: 2026-10-17
- フェーズ: 3
- 状態: 採用

仕様 7.9 では、メニューやツールチップのような一時的な窓(override-redirect)を親ウィンドウの映像に重ねて出す。ADR 0009 の `x11grab -window_id` では、Xvfb 上で親に重なった一時的な窓の部分が黒く抜けた(tkinter の試験用アプリ `tests/apps/popup.py` で確認)。そこで、取り込みを `-video_size`・`-grab_x`・`-grab_y` で画面上の親の範囲を取る方式に変えた。一時的な窓は X の上では親と同じ画面の位置に描かれるので、追加の処理なしで親の映像に重なって映る。ウィンドウ同士は dew が重ならない位置に置いているので、ほかのアプリのウィンドウは映り込まない。範囲は始めたときの位置と大きさで決まるため、親が動くか大きさが変わったら取り込みを作り直す(つないだままのブラウザは同じ WebSocket で新しい映像を受け取る)。性能は変わらない(1080p60 で 61 fps・遅延 48 ms)。親の範囲からはみ出した部分(ウィンドウの下端近くで開いたメニューなど)は映らない。これを映すには、取り込む範囲をはみ出した窓まで広げる(メニューを開くたびに取り込みを作り直すことになり、数百 ms 止まる)か、はみ出した一時的な窓を別の映像にしてブラウザ側で親の上に重ねる必要がある。どちらも重いので、フェーズ3では親に重なる部分だけとし、9.2 に残す。

追記(2026-10-18): 範囲で取り込むと、親からはみ出した一時的な窓が、隣に置いたほかのアプリのウィンドウの映像に映り込む(リモートでの確認で、4つほど開いたときに見つかった)。そこで監視が一時的な窓の位置も追い、ほかのアプリのウィンドウに重なったら、そのウィンドウを一時的な窓のない場所へ移す。窓の持ち主は、X のウィンドウ ID の上位ビット(作った接続ごとに決まる)で見分ける(Tk のメニューは `_NET_WM_PID` も `WM_TRANSIENT_FOR` も持たないため)。新しいウィンドウを置くときも、一時的な窓のある場所を避ける。あわせて、dew がウィンドウを動かしたときに、ウィンドウマネージャと同じく合成の ConfigureNotify(ICCCM 4.1.5)をアプリへ送るようにした。送らないと Tk などは元の位置のままだと思い、メニューを元の位置(ほかのウィンドウの上)に出していた。
