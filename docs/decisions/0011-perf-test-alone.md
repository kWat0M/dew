# 0011: 性能の受け入れテストは E2E の最後に単独で流す

- 日付: 2026-10-17
- フェーズ: 3
- 状態: 採用

フェーズ3の基準3(1080p 60fps で受信 fps 55 以上、遅延 150 ms 以下)は、単独なら 61 fps・遅延 49 ms で満たすが、E2E 全体を並列(24 コアで 12 ワーカー)に流すと 4 fps まで落ちた。並列実行の前半は各テストが Xvfb・ffmpeg・ブラウザを同時に立ち上げて load が 33 になり、テスト用アプリ自身の描画も 28 fps に落ちていたので、dew の遅さではなく測る条件が崩れていると判断した。仕様の想定は「サーバと同じホストの Chrome で測定」で、ほかの重い処理と同時に動く条件は含まない。そこで性能のテストを `tests/e2e/specs/phase3-perf.spec.ts` に分け、Playwright の perf プロジェクト(Chrome、chrome と firefox のプロジェクトに依存)で、ほかのテストがすべて終わってから1つだけ流す。テストの並列数を全体で下げる案は、全体の時間が延びるうえ CPU の取り合いを完全には避けられないので採らなかった。依存先のテストが失敗すると perf は流れないので、単独で確かめるときは `npx playwright test --project perf --no-deps` を使う。落ちたときにどこで詰まったか分かるよう、受信 fps とあわせてアプリが描いた fps もログに出す。

追記(2026-10-18): 全体を流すとたまに落ちていた、時間に厳しいテスト(フェーズ2の同期再生 2 つ「フレーム番号の差が1以内」と、フェーズ4の「直近30秒を巻き戻して再生できる」)も、`tests/e2e/specs/timing-perf.spec.ts` に移した。timing-chrome・timing-firefox プロジェクトで、perf の後に流す(2つは並べて流すが、どちらも軽い)。全体の時間は 1.8 分から 2.3 分ほどに延びるが、配布前の確認を毎回「全部通った」で終えられるようにするため。
